# EFFECTPLAN
# RFC 0001 — Ultra-Lightweight Deterministic Tool-Effect Planner

**Version:** 0.2.0  
**Status:** Proposed — architecture revision  
**Product:** EffectPlan  
**Package:** `@effectplan/core` (provisional; registry and trademark clearance required)  
**Category:** AI developer infrastructure / deterministic execution planning  
**Implementation:** Rust compiled to WebAssembly  
**Public interface:** TypeScript / JavaScript  
**Distribution:** One npm package  
**Maximum unpacked package size:** 50,000 bytes  
**Runtime dependencies:** Zero  
**Network requirement:** None  
**Model requirement:** None

# 1. EXECUTIVE DECISION

## 1.1 What we are building

EffectPlan is a tiny, deterministic, high-performance library that analyzes the declared resource effects of AI tool calls and produces a dependency graph for safe concurrent execution.

It allows an AI application or agent runtime to understand which operations can run independently and which must wait for other operations.

Example:

An agent requests:

- Read `src/a.ts`.
- Write `src/b.ts`.
- Update `src/a.ts`.
- Read `src/c.ts`.

EffectPlan identifies the resource conflicts and returns the required dependencies.

The host application remains responsible for executing operations.

## 1.2 Product objective

Build a reusable software primitive that:

1. Identifies resource-level conflicts between tool invocations.
2. Preserves the required ordering of conflicting operations.
3. Allows independent operations to be scheduled concurrently.
4. Uses argument-dependent resource identities rather than broad tool-level safety flags.
5. Produces deterministic, explainable execution plans.
6. Operates locally without models, network access or hosted services.
7. Fits inside a single npm package of no more than 50,000 bytes unpacked.

## 1.3 Product positioning

**EffectPlan — Resource-aware execution planning for AI tools.**

AI systems generate operation requests. EffectPlan calculates their dependencies using deterministic software.

It does not decide what an agent should do. It helps the host runtime determine which requested operations may be scheduled together under their declared effect contracts.

## 1.4 Architectural decision

```text
Developer Application
        |
        v
@effectplan/core
        |
        +-- TypeScript public API
        |
        +-- Typed-array input encoder
        |
        +-- WebAssembly loader
        |
        v
Single Rust WASM Engine
        |
        +-- Input validation
        +-- Resource indexing
        +-- Conflict detection
        +-- Dependency graph
        +-- Graph verification
        |
        v
Compact Execution Plan
```

## 1.5 Non-negotiable product constraints

- Exactly one public npm package.
- Exactly one WASM engine binary.
- No NAPI-RS.
- No platform-specific native addon packages.
- No `wasm-bindgen` runtime dependency.
- No `serde` in the WASM engine.
- No runtime allocator in the Rust engine.
- No runtime dependencies in the npm package.
- No external services.
- No mandatory telemetry.
- No model-provider integration.
- No framework requirement.
- No hidden tool execution.
- No unproven performance or security guarantees.

# 2. 50 KB DEFINITION AND PACKAGE BUDGET

## 2.1 What 50 KB means

For this RFC, the size limit is defined as:

**The sum of all unpacked files included in the published npm package MUST NOT exceed 50,000 bytes.**

This includes:

- JavaScript wrapper.
- WebAssembly binary.
- TypeScript declarations.
- Package metadata.
- README.
- License.

It excludes:

- Rust source code.
- TypeScript source code.
- Tests.
- Fixtures.
- Documentation source.
- Benchmark tooling.
- Development dependencies.
- CI configurations.

These remain in the source repository but are excluded from the published tarball.

## 2.2 Release budget

| Component | Maximum budget |
|---|---:|
| `effectplan.wasm` | 40,000 bytes |
| JavaScript wrapper and loader | 5,000 bytes |
| TypeScript declarations | 1,500 bytes |
| Package metadata, README and license | 3,500 bytes |
| **Total** | **50,000 bytes** |

These are allocation limits, not measured binary sizes.

The WASM binary target must be demonstrated by an actual optimized build.

If the WASM engine cannot fit within its allocation, the implementation must be optimized or reduced before release.

The total package may not exceed the hard limit.

## 2.3 Package size enforcement

Every release candidate must run a package-size verification script.

The build must:

1. Produce the distributable WASM.
2. Compile and minify the JavaScript wrapper.
3. Generate declarations.
4. Assemble the npm package.
5. Run `npm pack --dry-run --json`.
6. Calculate total unpacked file size.
7. Fail if the size exceeds 50,000 bytes.

The release must retain the file-by-file size report.

Compressed tarball size is reported separately.

## 2.4 Runtime memory is a separate budget

The installed package may be under 50,000 bytes while using more memory during execution.

This is expected.

The package-size limit must never be confused with WASM linear memory, JavaScript heap allocation or input buffer size.

Initial runtime limits:

- Maximum operations: 4,096.
- Maximum explicit resource accesses: 32,768.
- Maximum resource namespace length: 256 bytes.
- Maximum resource identifier length: 1,024 bytes.
- Maximum total input identifier bytes: 1 MiB.
- Maximum planning memory: 3 MiB for the default supported batch limits.

These defaults must be validated by benchmark and memory tests.

A host may configure lower limits.

# 4. EFFECT CONTRACT MODEL

## 4.1 Effect classifications

```typescript
export type EffectMode =
  | "pure"
  | "resources"
  | "exclusive"
  | "unknown";
```

| Mode | Meaning | Scheduling |
|---|---|---|
| `pure` | No externally observable resource effects are declared | May overlap subject to the global barrier model |
| `resources` | Explicit reads and writes are declared | Resource-aware planning |
| `exclusive` | Operation must not overlap another operation | Global exclusive barrier |
| `unknown` | Actual effects cannot be established | Conservative global exclusive barrier |

Default behavior for missing effects is `unknown`.

Strict policy may reject unknown effects instead of planning them.

## 4.2 Resource model

```typescript
export interface ResourceRef {
  readonly namespace: string;
  readonly id: string;
}

export type AccessMode = "read" | "write";

export interface ResourceAccess {
  readonly resource: ResourceRef;
  readonly mode: AccessMode;
}
```

Examples:

```typescript
const fileResource: ResourceRef = {
  namespace: "filesystem",
  id: "project-42:/src/index.ts"
};

const orderResource: ResourceRef = {
  namespace: "database",
  id: "tenant-7:orders:order-123"
};
```

Resource identity is the exact pair:

`namespace + id`

The engine MUST NOT independently interpret or normalize either field.

Examples of transformations the engine must not perform:

- Filesystem path resolution.
- Symbolic-link resolution.
- URL canonicalization.
- DNS lookup.
- Database collation.
- Tenant inference.
- Case folding.
- Unicode normalization.

The appropriate trusted adapter performs canonicalization.

## 4.3 Effect contract

```typescript
export interface EffectContract {
  readonly version: 1;
  readonly mode: EffectMode;
  readonly accesses?: readonly ResourceAccess[];
}
```

Rules:

- `pure` must not declare resource accesses.
- `resources` must declare at least one resource access.
- `exclusive` may declare known resources for diagnostic purposes.
- `unknown` may declare partial known resources but remains globally exclusive.
- Missing effect contract is `unknown`.
- Unknown effect policy defaults to `serialize`.
- Strict policy may use `reject`.

## 4.4 Resource access normalization

When one operation declares both read and write access to the same resource, the effective access is write.

Duplicate access declarations must not generate incorrect self-dependencies.

The TypeScript boundary normalizes duplicate accesses before encoding.

The Rust engine independently validates the packed contract structure.

## 4.5 Conflict matrix

| Earlier operation | Later operation | Dependency |
|---|---|---|
| Read R | Read R | No |
| Read R | Write R | Yes |
| Write R | Read R | Yes |
| Write R | Write R | Yes |
| Read R1 | Write R2 | No, if R1 and R2 are different |
| Write R1 | Write R2 | No, if R1 and R2 are different |
| Unknown | Any other operation | Yes |
| Exclusive | Any other operation | Yes |

All dependencies between operations in a batch point from an earlier input operation to a later one.

# 5. FORMAL SCHEDULING MODEL

## 5.1 Operation

Each operation contains:

- Unique call ID.
- Input index.
- Effect mode.
- Zero or more resource accesses.

## 5.2 Resource-indexed state

For every resource, the engine tracks:

```text
last_writer
readers_since_last_write
```

Internal state:

```rust
struct ResourceState {
    last_writer: u32,
    reader_head: u32,
}
```

Use `u32::MAX` as the empty sentinel.

## 5.3 Implicit global barrier

Reserve resource index `0` for an internal global barrier.

All ordinary operations acquire a read access to the barrier.

`exclusive` and `unknown` operations acquire a write access.

This guarantees:

- Earlier ordinary operations finish before a global exclusive operation.
- Later ordinary operations wait for the exclusive operation.
- Multiple ordinary operations can still overlap.
- Exclusive operations are ordered against one another.

This internal barrier is not exposed as a user resource.

## 5.4 Dependency rules

For a read:

1. If a previous writer exists, create a dependency on that writer.
2. Add the current operation to the resource's reader set.

For a write:

1. Depend on the last writer, if present.
2. Depend on all readers since the last write.
3. Clear those readers.
4. Set the current operation as the latest writer.

Self-dependencies must never be emitted.

## 5.5 Correctness properties

The planner must guarantee, relative to declared effects:

- No read/write conflict is omitted.
- No write/read conflict is omitted.
- No write/write conflict is omitted.
- Read/read operations remain independent.
- Distinct resource identities remain independent unless an explicit global barrier applies.
- Conflicting operations preserve input order.
- The dependency graph is acyclic.
- Unknown effects cannot be silently scheduled as pure.
- Identical input and configuration produce identical output.

## 5.6 Algorithm complexity

Let:

- N = number of operations.
- A = total explicit resource accesses.
- T = N + A, including implicit barrier accesses.
- E = emitted dependency records.

Target expected complexity:

`O(N + A + E)`

Target memory:

`O(N + A + E)`

No all-pairs operation matrix is allowed in production.

The implementation uses resource indexing, fixed-layout workspace and sparse dependency records.

The reference implementation used in tests may use a slower pairwise algorithm.

# 6. PUBLIC API

## 6.1 Package usage

```typescript
import { EffectPlan } from "@effectplan/core";

const planner = await EffectPlan.create();

const plan = planner.planBatch(calls);

const cursor = planner.createCursor(plan, {
  maxConcurrency: 8
});

const ready = cursor.takeReady();

cursor.markCompleted(ready[0].id);
```

The WASM module is loaded once for each planner instance.

After initialization, planning APIs are synchronous.

## 6.2 Required public types

```typescript
export interface ToolCall {
  readonly id: string;
  readonly effect?: EffectContract;
}

export interface PlanOptions {
  readonly unknownEffectPolicy?: "serialize" | "reject";
}

export interface CursorOptions {
  readonly maxConcurrency: number;
}

export interface PlanStatistics {
  readonly callCount: number;
  readonly resourceAccessCount: number;
  readonly dependencyCount: number;
  readonly unknownEffectCount: number;
  readonly exclusiveCount: number;
}
```

## 6.3 Public class

```typescript
export class EffectPlan {
  static create(
    options?: InitializationOptions
  ): Promise<EffectPlan>;

  planBatch(
    calls: readonly ToolCall[],
    options?: PlanOptions
  ): ExecutionPlan;

  createCursor(
    plan: ExecutionPlan,
    options: CursorOptions
  ): ExecutionCursor;

  explainDependency(
    plan: ExecutionPlan,
    predecessorId: string,
    operationId: string
  ): DependencyExplanation | undefined;

  validateEffectContract(
    contract: EffectContract
  ): ValidationResult;

  getEngineInfo(): EngineInfo;
}
```

## 6.4 Execution plan

The plan is an immutable public handle backed by private compact graph data.

```typescript
export interface ExecutionPlan {
  readonly version: 1;
  readonly callCount: number;
  readonly edgeCount: number;
  readonly statistics: PlanStatistics;
}
```

The internal typed arrays and resource mapping must not be exposed as mutable public state.

Use a private `WeakMap` or equivalent private ownership mechanism.

Version 0.1 plans are process-local objects. Portable plan serialization is deferred.

## 6.5 Execution cursor

```typescript
export interface ReadyCall {
  readonly id: string;
  readonly index: number;
}

export interface ExecutionCursor {
  takeReady(): readonly ReadyCall[];

  markCompleted(callId: string): void;

  markFailed(callId: string): void;

  getStatus(callId: string): OperationStatus;
}
```

The cursor manages scheduling state but does not execute operations.

### Cursor behavior

- `takeReady()` returns operations whose dependencies have completed.
- It never exceeds `maxConcurrency`.
- Ready calls use input order as a deterministic tie-breaker.
- `markCompleted()` releases dependent operations.
- `markFailed()` blocks dependent operations transitively.
- Independent operations may continue after a failure.
- The cursor never retries a failed operation automatically.
- Cancellation and compensation remain host responsibilities.

The host must call `markCompleted()` only after the actual operation has completed successfully.

## 6.6 Stable error codes

| Error | Meaning |
|---|---|
| `EP_INVALID_INPUT` | Invalid batch |
| `EP_DUPLICATE_CALL_ID` | Duplicate call ID |
| `EP_INVALID_EFFECT` | Invalid effect contract |
| `EP_INVALID_RESOURCE` | Invalid resource |
| `EP_UNKNOWN_EFFECT_REJECTED` | Strict policy rejected unknown effect |
| `EP_LIMIT_EXCEEDED` | Configured limit exceeded |
| `EP_INVALID_PLAN` | Invalid plan |
| `EP_INVALID_CURSOR_STATE` | Invalid scheduling state |
| `EP_ENGINE_UNAVAILABLE` | WASM could not initialize |
| `EP_ENGINE_ERROR` | Engine reported an internal error |

All errors must have stable machine-readable codes.

Error messages must not include raw resource identifiers by default.

# 7. WASM ABI AND DATA TRANSFER

## 7.1 Why a raw ABI

Do not use JSON serialization between JavaScript and Rust.

Do not use `serde` for the runtime boundary.

Do not call Rust individually for every operation.

Instead, prepare a compact batch and transfer it in one WebAssembly call.

## 7.2 Resource interning

The TypeScript wrapper assigns each distinct `(namespace, id)` pair a request-local integer resource ID.

Example:

```text
filesystem:project-1:file-a -> 1
filesystem:project-1:file-b -> 2
database:tenant-1:order-2   -> 3
```

Index `0` is reserved for the engine's internal global barrier.

The engine works with integer identifiers rather than repeatedly comparing strings.

The TypeScript wrapper retains the resource lookup table for diagnostics.

## 7.3 Input arrays

The batch is encoded as separate typed arrays.

| Array | Type | Meaning |
|---|---|---|
| `callModes` | Uint8Array | Effect mode for each call |
| `accessOffsets` | Uint32Array | Start/end range of resource accesses per call |
| `resourceIds` | Uint32Array | Interned resource IDs |
| `accessModes` | Uint8Array | Read/write mode |

The `accessOffsets` array has N+1 entries.

All arrays are prepared in JavaScript and copied into one aligned region of WASM linear memory.

## 7.4 Example packed input

```text
Call modes:
[1, 1, 1]

Access offsets:
[0, 1, 2, 3]

Resource IDs:
[1, 2, 1]

Access modes:
[WRITE, WRITE, READ]
```

The first and third operations address the same resource and therefore require ordering.

The second operation is independent.

## 7.5 Raw WASM function

The WASM engine exposes a single primary planning function.

Conceptual ABI:

```rust
#[no_mangle]
pub unsafe extern "C" fn effectplan_plan(
    abi_version: u32,
    call_count: u32,
    access_count: u32,
    resource_count: u32,

    call_modes_ptr: u32,
    access_offsets_ptr: u32,
    resource_ids_ptr: u32,
    access_modes_ptr: u32,

    workspace_ptr: u32,
    workspace_len: u32,

    output_ptr: u32,
    output_capacity: u32,
) -> i32;
```

This is a raw internal ABI.

It is not part of the public TypeScript API.

All pointer arithmetic, lengths, alignment and capacity checks must be validated before any access.

## 7.6 Workspace design

The TypeScript loader owns allocation of the WASM memory regions.

The Rust engine does not allocate memory dynamically.

Required workspace arrays:

- Last writer per resource.
- Reader-head per resource.
- Reader-next per access event.
- Reader-operation index per event.
- Temporary edge storage.
- Compact output header.

The engine receives the workspace pointer and length.

It validates the entire workspace before processing.

## 7.7 Output representation

The WASM engine returns compact dependency records:

```text
predecessor index
successor index
resource index
reason code
```

Dependency records must be sorted into a deterministic order.

The TypeScript wrapper builds the private execution-plan representation.

The public API returns only the immutable plan handle and statistics.

## 7.8 Edge capacity

Let T = N + A.

The implementation must prove and test its maximum edge bound.

For the proposed resource-state algorithm, each read event can create at most one dependency on its preceding writer and one dependency on a later write. Each write event can depend on the previous writer and the pending readers.

The initial allocation bound is therefore:

`maximum raw edge records <= 2 * T`

This bound is an implementation invariant that must be verified against the reference oracle and property tests.

If the algorithm changes, the bound must be recalculated.

## 7.9 Memory safety

Before executing the raw ABI:

- Validate ABI version.
- Validate call count.
- Validate access count.
- Validate resource count.
- Validate every pointer range.
- Validate integer overflow in size calculations.
- Validate `accessOffsets`.
- Validate mode values.
- Validate resource indices.
- Validate output capacity.
- Validate workspace capacity.

No unchecked pointer should be dereferenced before validation.

# 8. RUST IMPLEMENTATION

## 8.1 Target

Use:

`wasm32-unknown-unknown`

The Rust engine is a `no_std` implementation using the Rust core library.

Official Rust documentation describes this target as a minimal WebAssembly target with few assumptions about host capabilities. It supports core functionality and can be used for bare-bones WebAssembly applications.

## 8.2 No-runtime-allocation design

The production WASM implementation must not require:

- `HashMap`.
- `Vec`.
- `String`.
- `serde`.
- `wasm-bindgen`.
- `wasm-pack`.
- `tokio`.
- Native operating-system APIs.

Use caller-provided workspace and direct resource indexing.

The Rust source repository can still use normal test tooling outside the deployed WASM artifact.

## 8.3 Internal Rust structure

```rust
pub struct ResourceState {
    pub last_writer: u32,
    pub reader_head: u32,
}

pub struct Edge {
    pub predecessor: u32,
    pub successor: u32,
    pub resource_id: u32,
    pub reason: u32,
}

pub struct PlanStatistics {
    pub calls: u32,
    pub accesses: u32,
    pub edges: u32,
}
```

## 8.4 Function responsibilities

| Function | Purpose |
|---|---|
| `validate_input()` | Validate packed ABI structures |
| `validate_limits()` | Enforce maximum sizes |
| `initialize_workspace()` | Initialize request-local arrays |
| `process_barrier()` | Add implicit global effect |
| `process_read()` | Process read access |
| `process_write()` | Process write access |
| `emit_edge()` | Create dependency record |
| `build_plan()` | Process operations in input order |
| `sort_edges()` | Establish deterministic dependency order |
| `write_output()` | Write compact output |
| `set_error()` | Return stable error status |

All safety-critical operations must be covered by unit tests.

# 9. TYPESCRIPT IMPLEMENTATION

## 9.1 Responsibilities

The TypeScript wrapper is a thin API layer.

It is responsible for:

- Public API validation.
- Resource interning.
- Access normalization.
- Typed-array construction.
- WASM loading.
- WASM memory management.
- ABI invocation.
- Error mapping.
- Plan encapsulation.
- Cursor state.
- Dependency explanations.

It is not a second independent scheduling engine.

## 9.2 Function names and files

| File | Functions |
|---|---|
| `index.ts` | `EffectPlan.create()`, public exports |
| `loader.ts` | `loadWasm()`, `instantiateEngine()` |
| `memory.ts` | `ensureMemory()`, `allocateRegions()`, `createViews()` |
| `encode.ts` | `internResources()`, `encodeCalls()`, `normalizeAccesses()` |
| `planner.ts` | `planBatch()`, `validatePlanHandle()` |
| `cursor.ts` | `createCursor()`, `takeReady()`, `markCompleted()`, `markFailed()` |
| `explain.ts` | `explainDependency()` |
| `errors.ts` | `mapEngineError()`, `createPublicError()` |

## 9.3 Loader behavior

`EffectPlan.create()` is asynchronous because the WASM binary must be loaded and instantiated.

After initialization, `planBatch()` is synchronous.

The loader must:

- Work in supported Node.js versions.
- Work in supported browsers.
- Load the single package-local WASM asset.
- Validate ABI version.
- Fail clearly if WebAssembly is unavailable.
- Avoid network requests unless the consuming application explicitly provides a remote WASM source.
- Avoid silently falling back to a different implementation.

## 9.4 One package, two environments

The initial package supports:

- Node.js ESM.
- Modern browser environments with WebAssembly and ES2022 support.

CommonJS support is deferred.

The package must use the same WASM binary for both environments.

Node-specific file loading must not leak into the browser entry point.

Browser loading must support WebAssembly MIME-type differences by falling back to ordinary ArrayBuffer instantiation where needed.

## 9.5 Concurrency

Each `EffectPlan` instance owns its WASM memory.

Do not share mutable linear memory across concurrent planner instances.

The initial public planner API is synchronous after initialization.

Worker-thread and Web Worker offloading are deferred until benchmarks show that ordinary bounded batches block the event loop enough to justify the added code.

## 14.7 End-to-end tests

### Scenario A — Filesystem

Two writes target different files; a third write targets the same file as the first.

Expected: independent work overlaps; conflicting operations preserve order.

### Scenario B — Database

Different rows are modified concurrently; the same row is modified by two operations.

Expected: dependencies use declared row identities.

### Scenario C — Different tools, same resource

Two different tool definitions modify the same declared resource.

Expected: dependencies are detected across tool names.

### Scenario D — Multiple tenants

The same local resource ID occurs under two tenant namespaces.

Expected: no accidental cross-tenant collision.

### Scenario E — Unknown operation

One operation has no effect declaration.

Expected: global barrier or strict rejection.

### Scenario F — Failure

One operation fails while independent operations are running.

Expected: dependents are blocked; unrelated operations may continue.

The host remains responsible for cancellation of already-running work.

# 16. MEMORY AND BOUNDS

## 16.1 WebAssembly memory

WebAssembly linear memory is separate from the 50,000-byte package limit.

WebAssembly memory grows in pages, conventionally 64 KiB per page.

The TypeScript wrapper calculates required buffer space before growing memory.

## 16.2 Memory policy

- Fixed maximum input limits.
- Fixed maximum workspace size.
- No unbounded growth.
- No retained references to views created before memory growth.
- Recreate typed-array views after every memory growth.
- Reuse the WASM instance between normal planning batches.
- Clear request-local workspace before reuse where required.
- Never return mutable raw WASM memory views to the public API.

## 16.3 Buffer layout

The wrapper calculates aligned regions for:

1. Call modes.
2. Access offsets.
3. Resource IDs.
4. Access modes.
5. Resource state.
6. Reader linked-list state.
7. Dependency records.
8. Output statistics.

All size arithmetic must use checked integer operations.

# 22. ADVERSARIAL REVIEW

## Hidden assumptions

1. A 50 KB package can contain a sufficiently complete Rust WASM engine.
2. WebAssembly performs better than optimized TypeScript for the actual batch sizes.
3. Resource identities can be canonically supplied by host applications.
4. Developers are willing to declare resource effects.
5. The dependency graph produces better real-world concurrency than existing schedulers.

All five require evidence.

## Critical weaknesses

- WASM is not native Rust execution.
- Memory conversion can dominate small workloads.
- Bad effect declarations can still cause conflicting side effects.
- A tiny artifact does not imply tiny runtime memory.
- Browser and Node loading behavior must both be tested.
- A sophisticated planner can be slower than a simple serial strategy for tiny batches.

## Failure modes

- 50 KB target cannot be reached without removing necessary functionality.
- Packed ABI contains an incorrect offset or length.
- Dependency generation misses a conflict.
- Excessive edge generation consumes memory.
- Scheduler incorrectly releases a dependent operation.
- WASM startup dominates useful work.
- Browser bundlers fail to resolve the binary.
- The package is fast in Rust benchmarks but slow in real npm workloads.

## Stronger strategy

Make the first milestone a proof of feasibility:

- Single WASM binary.
- Raw ABI.
- No runtime allocation.
- One resource model.
- One correct conflict algorithm.
- One independently tested TypeScript API.
- One actual 50,000-byte npm artifact.

Only expand the feature surface after this milestone passes.

## Brutal verdict

**Architecture: Strong, conditional.**

**Product differentiation: Still requires external adoption evidence.**

**50 KB target: Aggressive and unproven until a real build exists.**

**Production readiness: Not yet.**

# 1. EXECUTIVE DECISION

## 1.1 What we are building

EffectPlan is a tiny, deterministic, high-performance library that analyzes the declared resource effects of AI tool calls and produces a dependency graph for safe concurrent execution.

It allows an AI application or agent runtime to understand which operations can run independently and which must wait for other operations.

Example:

An agent requests:

- Read `src/a.ts`.
- Write `src/b.ts`.
- Update `src/a.ts`.
- Read `src/c.ts`.

EffectPlan identifies the resource conflicts and returns the required dependencies.

The host application remains responsible for executing operations.

## 1.2 Product objective

Build a reusable software primitive that:

1. Identifies resource-level conflicts between tool invocations.
2. Preserves the required ordering of conflicting operations.
3. Allows independent operations to be scheduled concurrently.
4. Uses argument-dependent resource identities rather than broad tool-level safety flags.
5. Produces deterministic, explainable execution plans.
6. Operates locally without models, network access or hosted services.
7. Fits inside a single npm package of no more than 50,000 bytes unpacked.

## 1.3 Product positioning

**EffectPlan — Resource-aware execution planning for AI tools.**

AI systems generate operation requests. EffectPlan calculates their dependencies using deterministic software.

It does not decide what an agent should do. It helps the host runtime determine which requested operations may be scheduled together under their declared effect contracts.

| Component                            | Maximum budget   |
| ------------------------------------ | ---------------- |
| `effectplan.wasm`                    | 40,000 bytes     |
| JavaScript wrapper and loader        | 5,000 bytes      |
| TypeScript declarations              | 1,500 bytes      |
| Package metadata, README and license | 3,500 bytes      |
| **Total**                            | **50,000 bytes** |

These are allocation limits, not measured binary sizes.

The WASM binary target must be demonstrated by an actual optimized build.

If the WASM engine cannot fit within its allocation, the implementation must be optimized or reduced before release.

The total package may not exceed the hard limit.

## 2.3 Package size enforcement

Every release candidate must run a package-size verification script.

The build must:

1. Produce the distributable WASM.
2. Compile and minify the JavaScript wrapper.
3. Generate declarations.
4. Assemble the npm package.
5. Run `npm pack --dry-run --json`.
6. Calculate total unpacked file size.
7. Fail if the size exceeds 50,000 bytes.

The release must retain the file-by-file size report.

Compressed tarball size is reported separately.

## 2.4 Runtime memory is a separate budget

The installed package may be under 50,000 bytes while using more memory during execution.

This is expected.

The package-size limit must never be confused with WASM linear memory, JavaScript heap allocation or input buffer size.

Initial runtime limits:

- Maximum operations: 4,096.
- Maximum explicit resource accesses: 32,768.
- Maximum resource namespace length: 256 bytes.
- Maximum resource identifier length: 1,024 bytes.
- Maximum total input identifier bytes: 1 MiB.
- Maximum planning memory: 3 MiB for the default supported batch limits.

These defaults must be validated by benchmark and memory tests.

A host may configure lower limits.

# 4. EFFECT CONTRACT MODEL

## 4.1 Effect classifications

```
export type EffectMode =
  | "pure"
  | "resources"
  | "exclusive"
  | "unknown";
```

| Mode        | Meaning                                                | Scheduling                                      |
| ----------- | ------------------------------------------------------ | ----------------------------------------------- |
| `pure`      | No externally observable resource effects are declared | May overlap subject to the global barrier model |
| `resources` | Explicit reads and writes are declared                 | Resource-aware planning                         |
| `exclusive` | Operation must not overlap another operation           | Global exclusive barrier                        |
| `unknown`   | Actual effects cannot be established                   | Conservative global exclusive barrier           |

Default behavior for missing effects is `unknown`.

Strict policy may reject unknown effects instead of planning them.

## 4.2 Resource model

```
export interface ResourceRef {
  readonly namespace: string;
  readonly id: string;
}

export type AccessMode = "read" | "write";

export interface ResourceAccess {
  readonly resource: ResourceRef;
  readonly mode: AccessMode;
}
```

Examples:

```
const fileResource: ResourceRef = {
  namespace: "filesystem",
  id: "project-42:/src/index.ts"
};

const orderResource: ResourceRef = {
  namespace: "database",
  id: "tenant-7:orders:order-123"
};
```

Resource identity is the exact pair:

`namespace + id`

The engine MUST NOT independently interpret or normalize either field.

Examples of transformations the engine must not perform:

- Filesystem path resolution.
- Symbolic-link resolution.
- URL canonicalization.
- DNS lookup.
- Database collation.
- Tenant inference.
- Case folding.
- Unicode normalization.

The appropriate trusted adapter performs canonicalization.

## 4.3 Effect contract

```
export interface EffectContract {
  readonly version: 1;
  readonly mode: EffectMode;
  readonly accesses?: readonly ResourceAccess[];
}
```

Rules:

- `pure` must not declare resource accesses.
- `resources` must declare at least one resource access.
- `exclusive` may declare known resources for diagnostic purposes.
- `unknown` may declare partial known resources but remains globally exclusive.
- Missing effect contract is `unknown`.
- Unknown effect policy defaults to `serialize`.
- Strict policy may use `reject`.

## 4.4 Resource access normalization

When one operation declares both read and write access to the same resource, the effective access is write.

Duplicate access declarations must not generate incorrect self-dependencies.

The TypeScript boundary normalizes duplicate accesses before encoding.

The Rust engine independently validates the packed contract structure.

## 4.5 Conflict matrix

| Earlier operation | Later operation     | Dependency                     |
| ----------------- | ------------------- | ------------------------------ |
| Read R            | Read R              | No                             |
| Read R            | Write R             | Yes                            |
| Write R           | Read R              | Yes                            |
| Write R           | Write R             | Yes                            |
| Read R1           | Write R2            | No, if R1 and R2 are different |
| Write R1          | Write R2            | No, if R1 and R2 are different |
| Unknown           | Any other operation | Yes                            |
| Exclusive         | Any other operation | Yes                            |

All dependencies between operations in a batch point from an earlier input operation to a later one.

# 5. FORMAL SCHEDULING MODEL

## 5.1 Operation

Each operation contains:

- Unique call ID.
- Input index.
- Effect mode.
- Zero or more resource accesses.

## 5.2 Resource-indexed state

For every resource, the engine tracks:

```
last_writer
readers_since_last_write
```

Internal state:

```
struct ResourceState {
    last_writer: u32,
    reader_head: u32,
}
```

Use `u32::MAX` as the empty sentinel.

## 5.3 Implicit global barrier

Reserve resource index `0` for an internal global barrier.

All ordinary operations acquire a read access to the barrier.

`exclusive` and `unknown` operations acquire a write access.

This guarantees:

- Earlier ordinary operations finish before a global exclusive operation.
- Later ordinary operations wait for the exclusive operation.
- Multiple ordinary operations can still overlap.
- Exclusive operations are ordered against one another.

This internal barrier is not exposed as a user resource.

## 5.4 Dependency rules

For a read:

1. If a previous writer exists, create a dependency on that writer.
2. Add the current operation to the resource's reader set.

For a write:

1. Depend on the last writer, if present.
2. Depend on all readers since the last write.
3. Clear those readers.
4. Set the current operation as the latest writer.

Self-dependencies must never be emitted.

## 5.5 Correctness properties

The planner must guarantee, relative to declared effects:

- No read/write conflict is omitted.
- No write/read conflict is omitted.
- No write/write conflict is omitted.
- Read/read operations remain independent.
- Distinct resource identities remain independent unless an explicit global barrier applies.
- Conflicting operations preserve input order.
- The dependency graph is acyclic.
- Unknown effects cannot be silently scheduled as pure.
- Identical input and configuration produce identical output.

## 5.6 Algorithm complexity

Let:

- N = number of operations.
- A = total explicit resource accesses.
- T = N + A, including implicit barrier accesses.
- E = emitted dependency records.

Target expected complexity:

`O(N + A + E)`

Target memory:

`O(N + A + E)`

No all-pairs operation matrix is allowed in production.

The implementation uses resource indexing, fixed-layout workspace and sparse dependency records.

The reference implementation used in tests may use a slower pairwise algorithm.

# 6. PUBLIC API

## 6.1 Package usage

```
import { EffectPlan } from "@effectplan/core";

const planner = await EffectPlan.create();

const plan = planner.planBatch(calls);
```

## 6.4 Execution plan

## 6.5 Execution cursor

```
export interface ReadyCall {
  readonly id: string;
  readonly index: number;
}

export interface ExecutionCursor {
  takeReady(): readonly ReadyCall[];

  markCompleted(callId: string): void;

  markFailed(callId: string): void;

  getStatus(callId: string): OperationStatus;
}
```

The cursor manages scheduling state but does not execute operations.

### Cursor behavior

- `takeReady()` returns operations whose dependencies have completed.
- It never exceeds `maxConcurrency`.
- Ready calls use input order as a deterministic tie-breaker.
- `markCompleted()` releases dependent operations.
- `markFailed()` blocks dependent operations transitively.
- Independent operations may continue after a failure.
- The cursor never retries a failed operation automatically.
- Cancellation and compensation remain host responsibilities.

The host must call `markCompleted()` only after the actual operation has completed successfully.

# 7. WASM ABI AND DATA TRANSFER

## 7.1 Why a raw ABI

Do not use JSON serialization between JavaScript and Rust.

Do not use `serde` for the runtime boundary.

Do not call Rust individually for every operation.

Instead, prepare a compact batch and transfer it in one WebAssembly call.

## 7.2 Resource interning

The TypeScript wrapper assigns each distinct `(namespace, id)` pair a request-local integer resource ID.

Example:

```
filesystem:project-1:file-a -> 1
filesystem:project-1:file-b -> 2
database:tenant-1:order-2   -> 3
```

Index `0` is reserved for the engine's internal global barrier.

The engine works with integer identifiers rather than repeatedly comparing strings.

The TypeScript wrapper retains the resource lookup table for diagnostics.

## 7.3 Input arrays

The batch is encoded as separate typed arrays.

| Array           | Type        | Meaning                                       |
| --------------- | ----------- | --------------------------------------------- |
| `callModes`     | Uint8Array  | Effect mode for each call                     |
| `accessOffsets` | Uint32Array | Start/end range of resource accesses per call |
| `resourceIds`   | Uint32Array | Interned resource IDs                         |
| `accessModes`   | Uint8Array  | Read/write mode                               |

The `accessOffsets` array has N+1 entries.

All arrays are prepared in JavaScript and copied into one aligned region of WASM linear memory.

## 7.4 Example packed input

```
Call modes:
[1, 1, 1]

Access offsets:
[0, 1, 2, 3]

Resource IDs:
[1, 2, 1]

Access modes:
[WRITE, WRITE, READ]
```

The first and third operations address the same resource and therefore require ordering.

The second operation is independent.

## 7.5 Raw WASM function

The WASM engine exposes a single primary planning function.

Conceptual ABI:

```
#[no_mangle]
pub unsafe extern "C" fn effectplan_plan(
    abi_version: u32,
    call_count: u32,
    access_count: u32,
    resource_count: u32,

    call_modes_ptr: u32,
    access_offsets_ptr: u32,
    resource_ids_ptr: u32,
    access_modes_ptr: u32,

    workspace_ptr: u32,
    workspace_len: u32,

    output_ptr: u32,
    output_capacity: u32,
) -> i32;
```

This is a raw internal ABI.

It is not part of the public TypeScript API.

All pointer arithmetic, lengths, alignment and capacity checks must be validated before any access.

## 7.6 Workspace design

The TypeScript loader owns allocation of the WASM memory regions.

The Rust engine does not allocate memory dynamically.

Required workspace arrays:

- Last writer per resource.
- Reader-head per resource.
- Reader-next per access event.
- Reader-operation index per event.
- Temporary edge storage.
- Compact output header.

The engine receives the workspace pointer and length.

It validates the entire workspace before processing.

## 7.7 Output representation

The WASM engine returns compact dependency records:

```
predecessor index
successor index
resource index
reason code
```

Dependency records must be sorted into a deterministic order.

The TypeScript wrapper builds the private execution-plan representation.

The public API returns only the immutable plan handle and statistics.

## 7.8 Edge capacity

Let T = N + A.

The implementation must prove and test its maximum edge bound.

For the proposed resource-state algorithm, each read event can create at most one dependency on its preceding writer and one dependency on a later write. Each write event can depend on the previous writer and the pending readers.

The initial allocation bound is therefore:

`maximum raw edge records <= 2 * T`

This bound is an implementation invariant that must be verified against the reference oracle and property tests.

If the algorithm changes, the bound must be recalculated.

## 7.9 Memory safety

Before executing the raw ABI:

- Validate ABI version.
- Validate call count.
- Validate access count.
- Validate resource count.
- Validate every pointer range.
- Validate integer overflow in size calculations.
- Validate `accessOffsets`.
- Validate mode values.
- Validate resource indices.
- Validate output capacity.
- Validate workspace capacity.

No unchecked pointer should be dereferenced before validation.

## 9.3 Loader behavior

`EffectPlan.create()` is asynchronous because the WASM binary must be loaded and instantiated.

After initialization, `planBatch()` is synchronous.

The loader must:

- Work in supported Node.js versions.
- Work in supported browsers.
- Load the single package-local WASM asset.
- Validate ABI version.
- Fail clearly if WebAssembly is unavailable.
- Avoid network requests unless the consuming application explicitly provides a remote WASM source.
- Avoid silently falling back to a different implementation.

## 9.4 One package, two environments

The initial package supports:

- Node.js ESM.
- Modern browser environments with WebAssembly and ES2022 support.

CommonJS support is deferred.

The package must use the same WASM binary for both environments.

Node-specific file loading must not leak into the browser entry point.

Browser loading must support WebAssembly MIME-type differences by falling back to ordinary ArrayBuffer instantiation where needed.

## 9.5 Concurrency

Each `EffectPlan` instance owns its WASM memory.

Do not share mutable linear memory across concurrent planner instances.

The initial public planner API is synchronous after initialization.

Worker-thread and Web Worker offloading are deferred until benchmarks show that ordinary bounded batches block the event loop enough to justify the added code.

# 4. How we make it fast

The important optimization is not simply using Rust. It is reducing the cost of transferring data between TypeScript and WebAssembly.

Use a packed integer interface.

Instead of passing thousands of nested JSON objects into Rust, TypeScript maps resource identities to integer IDs and sends compact typed arrays.

Example:

```
const operations = new Uint32Array([
  0, 1, 1, // operation, resource, write
  1, 2, 0, // operation, resource, read
  2, 1, 0  // operation, resource, read
]);
```

The Rust engine receives the entire batch in one call.

It constructs the dependency graph and returns compact arrays.

No JSON serialization. No individual native calls per operation. No repeated allocation of nested objects.

### Rust optimization

Build and compare several configurations:

```
[profile.release]
opt-level = "z"
lto = true
codegen-units = 1
panic = "abort"
strip = true
```

Then test WebAssembly optimization with:

```
wasm-opt -Oz input.wasm -o effectplan.wasm
```

Binaryen also offers `-O3` for aggressive speed optimization. We must measure the speed/size trade-off rather than assume the smallest binary is the fastest.&#x20;

- Conflict detection.
- Dependency graph construction.
- Parallel execution planning.
- Ready-call discovery.
- Dependency explanations.
- Bounded input validation.
- Structured diagnostics.
- Backend information.

All are part of one public API.

# 6. Performance and quality gates

| Requirement              | Acceptance target                                                     |
| ------------------------ | --------------------------------------------------------------------- |
| Published package size   | ≤ 50 KiB unpacked                                                     |
| Runtime dependencies     | Zero                                                                  |
| Native platform packages | Zero                                                                  |
| WASM binaries            | One                                                                   |
| Core implementation      | Rust                                                                  |
| Data transfer            | Packed typed arrays                                                   |
| Planning                 | Deterministic                                                         |
| Correctness              | Matches reference planner                                             |
| Graph validity           | Always acyclic                                                        |
| Unknown effects          | Fail closed                                                           |
| Native/WASM comparison   | ≤ 1.5× native Rust baseline for representative medium/large workloads |
| Test coverage            | Critical scheduling logic fully covered                               |
| Platform support         | Node.js and supported browser runtimes                                |

The 1.5× performance figure is a proposed target, not a measured result. Cold-start and warm-execution performance must be measured separately.

One important distinction: a 50 KiB package does not imply a 50 KiB memory footprint while processing large graphs. Runtime memory needs its own limits.

# 7. What we deliberately remove

To protect the footprint, we will not include:

- NAPI-RS.
- Serde JSON in the WASM boundary.
- Tokio.
- External runtime dependencies.
- A JavaScript fallback engine.
- A CLI.
- MCP server implementation.
- Telemetry SDKs.
- Dashboard functionality.
- Native binaries for each platform.

This does not mean those integrations can never exist. They can be independent future adapters, but they are not part of this 50 KiB package.

## Final architecture decision

# EffectPlan 0.1

Architecture selected

One package. One Rust core. One portable WASM binary.

- Distribution: `npm install @effectplan/core`
- Implementation: Rust compiled to WASM.
- API: TypeScript.
- Footprint: Maximum 50 KiB unpacked.
- Runtime dependencies: Zero.
- Execution: Offline, deterministic.
- Platforms: Portable JavaScript/WASM environments.

My one non-negotiable rule: If the first compiled WASM version cannot meet the 50 KiB budget and correctness requirements, we optimize the implementation before weakening the budget. We will not advertise 50 KB until `npm pack` proves it.
