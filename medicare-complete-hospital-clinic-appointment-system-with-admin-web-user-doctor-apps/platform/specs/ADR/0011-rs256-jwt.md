# ADR 0011 — RS256 JWT interop verifier (budget-gated)

Status: **Proposed** (2026-10-04) · Gate: Wave 9 advanced backlog (docs/19,
"Advanced backlog") · Implementation: none — requires a fresh D-62 budget
decision (or a documented swap) before any code.

## Context

`crates/web/http/src/jwt.rs` (B-22 / report R5) ships an opt-in stateless
JWT interop verifier behind `app.jwt`: `alg = HS256` only, `none` and every
other algorithm rejected before any crypto runs, mandatory `exp`, the
signature recomputed over the exact received `header.payload` ASCII
substring (RFC 7515 signing input) and compared in constant time, all
failures collapsing to the same `401` — built on the existing sha2-based
HMAC ("no second HMAC implementation, no new crate"). Hashed PAT +
HMAC session stays the default auth model.

RS256 (RSASSA-PKCS1-v1_5 + SHA-256) is the algorithm external identity
providers (Auth0/Keycloak/Okta-style) default to, so accepting
externally-issued RS256 bearer tokens would extend the same interop story
to key-pair-issued tokens. Verification requires an RSA implementation;
crypto is never hand-rolled (the program's hand-rolled posture covers
parsers and grammars only). `ring` already exists in the dependency graph
transitively (`Cargo.lock`: ring 0.17.14) — but promoting it to a *direct*
dependency makes it a direct external against D-62, and the cap is SPENT:
25/25 after the Wave 9 wasmtime amendment.

Constraints:

1. Budget posture: adoption needs either a D-62 amendment (cap 25 -> 26,
   recorded in DEPENDENCY-POLICY) or a swap (remove one direct external,
   documented in the same ledger).
2. Security posture must not regress: no algorithm-confusion oracle — a
   dual-algorithm deployment must select the key by configuration
   (issuer / `kid` -> key), never by a token-chosen `alg` against a
   shared key slot.
3. Interop scope stays B-22's: opt-in verifier, `exp` mandatory, one
   indistinguishable `401`, revocation out of scope.

## Decision

RS256 remains decision-gated: no implementation until a fresh budget
decision is recorded. The gate conditions if it passes:

- **Budget**: promote `ring` (the recorded option — the same audited
  crypto provider already in-tree behind rustls) to a direct dependency
  under an explicit D-62 amendment, OR swap a direct external for it;
  DEPENDENCY-POLICY carries the new count, and the license review is
  already settled (ring: ISC / MIT / BSD-2-Clause — allowlist unchanged).
- **Verifier shape**: algorithm-pinned verifiers — the existing HS256
  verifier stays byte-identical, and an RS256 verifier is a separate,
  separately-configured key slot (static PEM public key(s) or a `kid`
  allowlist), both opt-in behind `app.jwt`. The token header never picks
  between two key slots inside one verifier.
- **Key distribution**: static PEM from config first. A JWKS/HTTP fetch
  is a *separate* egress decision (it inherits the network-posture review
  recorded in ADR 0012) and is out of scope for the first landing.
- **Evidence**: the algorithm matrix (HS256 accepted, RS256 accepted with
  the right key, wrong key / `none` / `alg`-swap rejected before any
  crypto runs, mandatory `exp`, one `401` collapse) lands in the EXISTING
  keel-http suite (suite count stays 150).

Alternatives considered: a fresh `rsa` crate (same budget cost, no
advantage over the in-tree provider), hand-rolling RSA (refused outright —
crypto is never hand-rolled), an out-of-process verifier (budget-neutral
but adds an operational dependency for a single algorithm).

## Consequences

- Nothing moves now: no code, no tests, no budget-ledger change — the
  externals cap stays 25/25, and RS256 stays listed as a
  decision-gated candidate in docs/18 §26.2.
- This document is the gate artifact: implementation starts only when the
  budget decision is recorded (the ADR then flips Proposed -> Accepted
  with the amendment/swap reference).
- JWT-as-default-auth remains a permanent exclusion (docs/18 §26.3);
  RS256 would extend the opt-in interop verifier, never the auth model.
