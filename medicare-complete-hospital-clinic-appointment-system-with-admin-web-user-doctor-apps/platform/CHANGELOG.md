## [Unreleased]

### Changed

- **Phase T (part 1) - the templates are compiled into the console, so a
  published `kelson` binary can generate a project at all.**

  **The gap.** `kelson new` located its templates by joining the workspace root
  with `templates/starter-template` and reading them off disk. That works in a
  checkout and nowhere else: a stranger who installed the console from crates.io
  had no checkout beside them, so the command failed with `templates/... is
  missing under ...`. The framework's front door did not open for the audience
  the distribution program exists for. One level up, `workspace_root()` was
  required even for `--standalone`, the one layout whose entire point is that it
  needs no enclosing workspace, so `kelson new blog --standalone` in an empty
  directory failed before it ever reached the templates.

  **Why a crate, rather than an inline `include_str!` table.** Cargo packages a
  crate's own directory and nothing above it. An
  `include_str!("../../templates/...")` in `tools/kelson-console` compiles
  happily inside a checkout and then fails to compile for everyone who downloads
  the crate, because the files it names were never shipped. So the templates
  stay exactly where STAGE-0-SPEC §2 records them, `platform/templates/`, and a
  new `kelson-templates` crate sits *at* that path with those files inside its
  own root: one source of truth, the frozen topology record stays literally
  true, and the bytes survive being published. The crate has no dependencies and
  no code beyond two `&'static str` tables.

  **Precedence.** A checkout still wins whenever its templates are present, so a
  contributor editing one sees the change on the next run without a rebuild. The
  compiled-in copy is the fallback for everything else, and a test asserts the
  two are equal — which is what makes them one behaviour rather than two.

  **Line endings are normalised at the source, not left to the machine.**
  `core.autocrlf` decides the line endings of the work-tree files, and of the
  bytes compiled into a binary built on Windows. Left alone, the same commit
  would generate different bytes depending on who built it. Both paths now
  normalise to LF, so a project generated from a checkout and one generated from
  an installed binary of the same version are identical.

  **A defect this uncovered, and why it had survived.** `toml_path` emitted
  `Path::canonicalize`'s Windows verbatim form unmodified, so every `--deps-root`
  run on Windows produced `path = "//?/C:/..."`, which cargo reads as a URL and
  refuses to parse — leaving a project that would not build at all. It went
  unnoticed because the Phase Q verification generated through the implicit
  checkout, which `workspace_root()` builds without canonicalizing and so never
  carried the prefix. `--deps-root` is the only route to a standalone project
  until the kelson crates are on crates.io, which made it exactly the path a
  stranger would have hit first. Fixed in `toml_path` (the UNC form keeps its
  leading double slash) and pinned by a test across all four path shapes.

  **What `--standalone` requires now.** Nothing above the cwd. It still needs
  somewhere to take the kelson dependencies from, because those crates are not
  published yet: `--deps-root <checkout>`, or an enclosing workspace. With
  neither it refuses and says why, rather than emitting version-only specs that
  would parse and then fail to build on the very machine it was meant to help.
  That route opens up when Phase T publishes.

  **The architecture gate learned a class.** `templates` is a new topology class,
  following the `Framework` and `Extension` precedent: STAGE-0-SPEC §2 stays
  frozen, and the addition is recorded here. Its allow-list is empty, because
  the crate depends on nothing, and only the `Tools` class may depend on it —
  materialising template data is what scaffolding tools do. A library or runtime
  reaching for templates is now a violation.

  **Honest limits.**
  - Version-style standalone dependencies remain unverifiable. Nothing in this
    tree depends on them and they cannot be `cargo check`ed until Phase T
    publishes; only the `path` form is proven.
  - The embedded copy is a snapshot taken at build time. In a checkout the disk
    copy is used, so the two can only diverge if someone edits a template and
    does not rebuild — which the equality test catches on the next run there.
  - `kelson new <name>` without `--standalone`, in a directory with no workspace
    above it, still refuses. That is the in-workspace layout, which needs a
    workspace to join; the message now says so and points at `--standalone`.
  - No integration test drives the real binary from an empty directory. The
    behaviour was proven by running the built `kelson.exe` from a scratch
    directory with no `Cargo.toml` anywhere above it (exit 0, 13 files,
    `cargo check` clean, 85 packages locked); that probe is not checked in.

  **Gates.** keel-platform 1511 passed / 1 failed / 3 ignored, that failure
  being the known 50 ms hot-reload timing flake, which passes 3/3 when re-run in
  isolation — 1512 in effect; root 1438 / 0 failed / 3 ignored. Both are the
  Phase S baseline plus the 8 new tests. `clippy --workspace --all-targets -D
  warnings` clean in both trees, the architecture gate 3/3 in both, `xtask` 2/2
  both, and `your-app` builds with `cargo test --locked` exiting clean and its
  own lock untouched.

- **Phase S - the release now carries a migration manifest, so `kelson upgrade`
  can tell an operator which framework schema changes they owe.**

  **The gap.** Installing a newer kelson was a blind step. The release manifest
  recorded version, profile, artifacts, git identity and rustc, but nothing
  about schema — so an operator who had just upgraded the framework had no way
  to learn which migrations that release shipped, and no way to notice that a
  migration they had already applied had since been edited out from under them.

  **What the release records now.** `kelson build` enumerates
  `database/migrations-pairs` and writes each pair's base filename plus a
  SHA-256 of its `.up.sql` body into the manifest. Discovery follows the same
  contract the migration runners enforce — `<ts>_<name>.up.sql` with a required
  sibling `.down.sql`, filename-ordered — and is fail-closed for the same
  reasons: a missing `.down.sql`, an orphan `.down.sql`, or a malformed base
  name aborts the build rather than producing a manifest that silently omits a
  migration and later reports a false all-clear. A missing directory is not an
  error; a project with no pair migrations yet is normal.

  **Why the hash is the point.** `keel_migrations` stores only the migration
  *name*. That is enough to answer "has this been applied", and not enough to
  answer the question that actually bites: if a shipped migration is edited
  after the release was built, the database still reports it as applied,
  `kelson migrate` will never run it again, and nothing anywhere notices that
  the bytes no longer match what was applied. The recorded digest makes that
  case visible, and `kelson upgrade` reports it as `changed` rather than as an
  ordinary add or remove — because it is not ordinary.

  **The report.** `kelson upgrade` now diffs the manifest's shipped set against
  the tree's current one and classifies each difference as added, removed, or
  changed, with the changed case spelled out in full: the database holds the
  bytes that were originally applied, and re-running `kelson migrate` will not
  reapply them. The live applied-vs-pending comparison still belongs to
  `kelson migrate:status`, which needs a database; `upgrade` stays read-only and
  offline, and says where to go for the rest.

  **Backwards compatibility, tested.** The field is `#[serde(default)]`, so a
  `release.json` written before this phase still reads, as an empty set. An
  operator upgrading the console should not have their existing manifest
  rejected by the newer binary.

  **Two things found while proving it.**

  1. The drift computation started inline in the console, where nothing could
     test it. It was extracted to `kelson_deployment::migration_drift`, so the
     classification the operator reads is covered directly rather than only
     through the crate's other tests.
  2. `your-app` carries its own `Cargo.lock`, and adding `sha2` to
     `kelson-deployment` invalidates it — the `--locked` gate there fails until
     it is regenerated. All three locks (`keel-platform`, `platform`,
     `your-app`) were regenerated, and each diff is exactly one line: the
     `"sha2",` edge. No version moved.

  **Correction to an earlier record.** Previous entries describe `your-app` as
  passing "3/3". It has no test files at all; `cargo test` there reports three
  empty targets. Its gate is that it builds and `cargo test --locked` exits
  clean, which it does.

  **Honest limits.** This tree currently ships **zero** pair migrations, so the
  new console branch is dormant in a real run here — `kelson upgrade` reports
  "no release manifest" and says nothing further. The behaviour is proven by
  nine library tests, including one that pins the SHA-256 of an empty file
  against a known constant, one that edits a migration while keeping its name
  and asserts it surfaces as `changed` rather than `added`, and one that
  verifies a pre-Phase-S manifest still deserialises. It is not claimed to have
  been exercised against a populated manifest in this tree.

  Nine new tests in each workspace: `keel-platform/` **1504 / 0 failed / 3
  ignored / 158 binaries** and `platform/` **1430 / 0 / 3 / 155**;
  `clippy --workspace --all-targets -D warnings` clean in both; `xtask` 2/2 in
  both trees; `your-app` builds and tests clean under `--locked`.

- **Phase R - the local dev loop is working again: `kelson serve`, `kelson call`,
  `kelson shell` and `kelson model:prune` had all been failing to boot since
  Phase P.**

  **The regression.** Phase P gated the appointments/oauth2 module *registrations*
  behind `--features demo` (default off) so the harness could be published
  without dragging unpublished crates into the dependency graph. That is the
  right call for a release build. But none of the four local commands passed the
  feature, and they did not merely boot a module-less server - they refused to
  start at all:

      Error: UnknownDependency { provider: "module.demo", depends_on: "module.appointments" }

  The cause was an inconsistency Phase P left behind: `DemoModuleProvider`
  always registers itself, and its `dependencies()` named the two demo module
  providers unconditionally, while those providers were now only registered
  under the feature. Every non-demo boot therefore failed dependency
  resolution - and since `serve`/`call`/`shell`/`model:prune` all spawn
  `cargo run -p kelson-demo` without `--features demo`, the entire local
  development loop was dead.

  **Why nothing caught it.** No test ever *spawns* the harness through those
  CLI paths. The workspace test command itself passes `--features demo`, so
  `kelson-demo` compiled and its own tests all passed - the failure only exists
  in the `cargo run -p kelson-demo` invocations the console issues at runtime.

  **The fixes.**

  1. All four spawn sites now go through a single `demo_run_args()` helper that
     returns `run --quiet -p kelson-demo --features demo`. One implementation
     rather than four copies, so the flag cannot drift out of one of them
     again. The feature is inserted as a *cargo* argument, before any `--`.
  2. `DemoModuleProvider::dependencies()` now mirrors what is actually
     registered, so the declared edges match reality instead of asserting
     providers that may not exist.
  3. A non-demo build now fails fast with a message that says so, instead of
     dying at a boot gate that names none of it.

  **A second defect the first fix exposed.** Removing the `UnknownDependency`
  did not make the bare build bootable, because a second inconsistency sits
  behind it: `discover_manifests` scans `applications/*/module.toml` off disk
  *unconditionally*, so the appointments graph is present even when the
  providers that register its route-binding resolvers are compiled out. The
  feature gates the code, not the data, and the boot then dies at:

      GRAPH-BINDING-RESOLVER: module appointments: route DELETE
      /api/v1/appointments/{id} binds model Appointment but no resolver is
      registered in route.bindings

  `kelson-demo` is therefore a demo harness that genuinely requires the
  feature - which is exactly what the new startup message now says. Recorded
  here rather than papered over: making a bare `kelson-demo` boot a truly
  empty platform would mean also gating graph discovery, and that is a design
  decision for the host-split work rather than a silent change slipped into a
  bugfix.

  **Proof, not assertion.** Before: `cargo run -p kelson-demo -- --prune`
  exited 1 on `UnknownDependency`. After the dependency fix it exited 1 on the
  honest `GRAPH-BINDING-RESOLVER` message; after the fast-fail it exits 1 with
  the explicit "built without --features demo" explanation. With the feature -
  which every local command now passes - `cargo run -p kelson-demo --features
  demo -- --prune` exits 0. Two tests pin the invariants: the console asserts
  `demo_run_args()` carries the feature *before* any `--`, and `kelson-demo`
  asserts its declared module edges exist exactly when those providers are
  registered - a check that flips correctly in both configurations and passes
  under each.

  Gates at baseline plus the two new tests in both workspaces: `keel-platform/`
  **1495 / 0 failed / 3 ignored / 158 binaries** and `platform/` **1421 / 0 / 3 /
  155**; `clippy --workspace --all-targets -D warnings` clean in both *and* in
  the non-demo configuration of `kelson-demo`; `xtask` 2/2 in both trees;
  `your-app` 3/3. `Cargo.lock` untouched.

- **Phase Q - `kelson new` ships a standalone auth+CRUD starter: `--standalone`
  emits a self-contained project, and the starter template implements full CRUD
  instead of one COMMAND + one READ.**

  **Standalone.** `kelson new <name> --with-starter --standalone` no longer
  requires an enclosing cargo workspace. The generated crate lands at `./<name>`
  rather than `applications/<name>`, is never registered as a workspace member,
  and its manifest is rewritten to be self-contained. `{ workspace = true }` is
  eliminated everywhere - package fields are spelled out (version, edition,
  rust-version, license), the seven kelson crates get `version` + `path` pairs
  aimed at a checkout (`--deps-root`, defaulting to the workspace we are running
  inside), and third-party crates keep the exact pinned specs the platform
  itself builds against. A `[workspace]` table is inserted so cargo cannot adopt
  the project into whatever encloses it. An unresolvable dependency is a hard
  error at generation time, not a manifest that only fails later on someone
  else's machine. Only the manifest changes shape: every other template file is
  byte-identical between the two layouts.

  **Proof, not assertion.** A generated standalone project resolves 85 packages
  and passes `cargo check` plus its full suite - **5 passed / 0 failed**, no
  warnings. The in-workspace path is unchanged: a probe generated without
  `--standalone` still registers as a workspace member, keeps all 16
  `workspace = true` entries and carries no `[workspace]` table.

  **Full CRUD.** The starter gains `read`, `update` and `delete` alongside
  `create` and `list`: three new operation handlers, `notes.read` /
  `notes.update` / `notes.delete` routes sharing the `/notes/{id}` address
  (GET / PUT / DELETE), `note.updated` and `note.deleted` events, and a
  `full_crud_roundtrips` test that creates, reads, updates, re-reads, deletes,
  and then proves the row is **gone** - a read after delete is `KSN_NOT_FOUND`,
  not an empty payload.

  **Three defects the probe surfaced, fixed rather than papered over:**

  1. `codes` was imported at crate root but only used by tests, so every
     generated project carried an `unused_imports` warning on `cargo check`.
     Moved into the test module where it belongs.
  2. `MutationRecord` is asymmetric - `before: Option<Value>` but `after: Value`.
     The delete handler had them backwards; a delete now records
     `before: Some(...)` with `after: json!(null)`, which is the shape that
     actually describes "the row is now nothing".
  3. Two tests pinned the old two-operation contract (`operations.len() == 2`
     and `bundle.len() == 2`); both now derive from the new `ALL_OPS` constant,
     so the next capability added cannot silently desynchronise them.

  **A gap recorded, not hidden:** `new_project` still reads templates from disk
  via `walk_files`, so a *published* `kelson` binary would have no checkout to
  read them from. Template embedding is a Phase T prerequisite and is
  independent of `--standalone`. Version-spec dependencies
  (`kelson-foundation = "0.1.0"` with no `path`) likewise only resolve once the
  crates are on crates.io, which is why `--standalone` targets a local checkout
  today rather than pretending to work against an unpublished registry.

  Gates at exact baseline in both workspaces: `keel-platform/` **1493 / 0 failed
  / 3 ignored / 158 binaries** and `platform/` **1419 / 0 / 3 / 155**;
  `clippy --workspace --all-targets -D warnings` clean in both; `xtask` 2/2 in
  both trees; `your-app` 3/3. `Cargo.lock` untouched.

### Fixed

- **Module pins now gate what actually executes, instead of being written and
  never read.** `kelson promote` wrote `storage/framework/module-pins.json` and
  `kelson rollback` restored it, but nothing that ran ever opened the file. The
  promote-time stage-1 probe read it, so a *promotion* would fail on a drifted
  pin — while a process that was already running, or anything that loaded the
  plugins outside a promotion, ignored the pin entirely and ran whatever version
  happened to be installed. The pin was a record with no enforcement point, and
  a rollback that restores a version field nothing consults restores nothing.

  `kelson-registry` is now the canonical reader. `PackageIndex::module_pins`
  reads the file and `verify_pins_against_index` enforces it; both are called
  from four places — `load_wasm_plugins` (before any guest is instantiated),
  `kelson check`, `kelson graph`, and the `post_deploy` probe, which previously
  carried its own copy of the same rule. One rule, one reader, so the promote
  gate and the boot gate cannot drift into disagreeing about what "pinned"
  means. `MODULE_PINS_PATH` moved from the console to the registry and the
  console re-exports it, so existing paths keep working.

  **A behaviour change this introduced, stated rather than buried.** The old
  probe treated a *missing* pin file as fatal, while `ModulePinAdapter::read`
  seeded from the index for that same missing file — two adapters, one
  artifact, two meanings. A missing pin file now means "no pins declared" and
  is not an error, on both paths. This is what makes the boot gate safe to add:
  pinning stays opt-in and a workspace that has never run `kelson promote`
  boots exactly as before. A pin file that exists but is malformed still
  refuses, on both paths — an operator who wrote pins and mistyped one must not
  have every pin silently skipped.

  **What is enforced.** Every pinned module must be installed as a `[[wasm]]`
  entry, and the installed version must equal the pinned version. A pin naming
  a module that is installed as a `[[package]]` is refused too, because pins are
  written from the WASM index and a pin naming anything else is a
  misconfiguration that would otherwise never be noticed. `kelson check` prints
  `MODULE-PIN-MISMATCH` and exits non-zero, so CI catches it before deploy;
  `kelson graph` reports the pin state, printing "(none declared)" explicitly so
  "no pins" and "pins not checked" are distinguishable.

  **Honest limits.**
  - The gate is version-string equality. It does not hash the pinned bytes, so
    two different binaries both labelled `0.4.0` are indistinguishable; that is
    the artifact-digest work in M4, not this.
  - The registry's pin reader is exercised from the boot and console paths;
    there is no test that drives the real `kelson promote` binary end to end
    against a drifted pin. The probe calls the same function the tests cover.

  3 ignored, against the 1366 baseline: +11, which is 7 new registry pin tests
  and 4 new boot tests in the WASM facet suite. `cargo clippy --workspace
  --all-targets -D warnings` clean (6m 44s).

- **Wave A (part 1) — ABI v2 is a decided path rather than an open deferral:
  ADR 0019 records the reconsideration trigger, the migration shape and the
  versioning rule. A decision record; no code changes.**

  **The gap.** Two records pointed opposite ways. Root-tree ADR 0016
  (`platform/specs/ADR/0016-wasm-module-abi.md`, untracked and owned by the
  0.2a port) had *accepted* keeping the hand-rolled core-module ABI v1 and
  deferring WIT / the Component Model, while the distribution plan had adopted
  "Design ABI v2 on the WebAssembly Component Model" as Wave A. Whichever lost
  would have been silently falsified — one record would have gone on asserting a
  deferral the other was actively reversing, and nobody reading either could
  tell which one was live.

  **Why ADR 0019 amends 0016 instead of replacing it.** 0016 §2 does not reject
  the technology; it sets a reconsideration trigger *and* a migration shape —
  "an explicit ABI v2 with both ABIs supported through a transition window —
  never as a silent swap". Building on those terms means v1 keeps serving and
  nothing is swapped underneath an operator. 0016 is untracked and belongs to a
  concurrent workstream, so it is cited, never edited: the amendment lives in
  `keel-platform/specs/ADR/0019-wasm-abi-v2-component-model.md`, numbered 0019
  to continue past 0014-0018 rather than collide with them when the trees
  converge under ADR 0014.

  field defaults through `default_api()`, which returns `MODULE_ABI` itself

  pin the field. ABI v2 is therefore versioned by artifact *shape* (core module
  => v1, component => v2) with an explicit optional `abi` key on the `[[wasm]]`
  sidecar so review stays fail-closed, and `MODULE_ABI` stays `1`. The gap is

- **Wave A (part 2) — the staged `prepare → commit → drain` lifecycle is now
  enforced rather than specified: a WASM generation the host has not committed
  cannot dispatch, and one being drained cannot be resurrected.**

  **The gap.** ADR 0016 §3 deferred `prepare → commit → drain`, `docs/15-EXTENSION.md`
  described lifecycle states with no code behind them, and ADR 0019 §6 then
  sequenced the lifecycle as an ADR 0019 deliverable — three records describing
  one mechanism and none of them able to prove it ran. It is also the only Wave A
  deliverable that does not depend on the unresolved component-fixture risk
  (§6), so it could land on its own terms instead of waiting behind an open
  question.

  **What changed.** `kelson_wasm::PluginState` runs `Prepared -> Ready ->
  Draining -> Drained` (`keel-platform`
  `crates/extension/wasm/src/lib.rs:171`). `WasmHost::prepare`
  (`keel-platform` `crates/extension/wasm/src/lib.rs:574`) compiles, links,
  ABI-checks and drift-checks, then stops with **no** registration, so a failure
  in that phase leaves whatever was already serving untouched;
  `WasmHost::load` (`keel-platform`
  `crates/extension/wasm/src/lib.rs:707`) is that plus `commit`, so every
  existing caller still gets a dispatchable plugin and no call site had to
  change. `WasmPlugin::call` refuses anything but a `Ready` generation
  (`keel-platform` `crates/extension/wasm/src/lib.rs:925-932`), reading the
  state *after* it increments the in-flight counter: a call that read `Ready`
  first and incremented second could land in a generation `drain` had already
  declared idle and run guest code against a retired plugin, so reading second
  is what makes the pair airtight. `commit` (`keel-platform`
  `crates/extension/wasm/src/lib.rs:804`) is idempotent going forward but
  refuses to leave `Draining` or `Drained`; `drain` (`keel-platform`
  `crates/extension/wasm/src/lib.rs:835`) refuses new calls, waits for the
  in-flight ones, and on timeout reports how many it did **not** see finish
  instead of claiming a completion it never observed — staying retired rather
  than reopening mid-retire. The refusal is a new `WasmError::Lifecycle` variant
  (`keel-platform` `crates/extension/wasm/src/lib.rs:252`). Production boot
  uses the split form (`keel-platform` `runtime/kelson-demo/src/lib.rs:78`
  prepares, `:85-87` commits), so the host's registration decision is a
  separate, visible act rather than an implication of having called `load`.

  **Evidence.** Four tests in `keel-platform`
  `runtime/kelson-demo/src/wasm_tests.rs:891`, `:951`, `:1005` and `:1031` pin
  refusal-before-commit, one-way drain, refusal to drain a never-committed
  generation, and a drain that waits on a running guest and reports the wait it
  could not finish. `clippy --workspace --all-targets -- -D warnings` is clean
  and the suite moves 1388 → **1392 passed, 0 failed, 3 ignored** across 160
  suites (+4, all of them the tests above). Claim 16 moves ABSENT → PARTIAL: the
  mechanism exists for plugin generations, while `ModuleState` and the
  `DEGRADED`/`DISABLED` states remain backlog, and `docs/15-EXTENSION.md` now
  says that plainly instead of calling the whole lifecycle deferred.

  **Deliberately not shipped.** No new `KSN_*` code and no new HTTP pin. A call
  refused while draining deserves 503, but nothing can produce that state until
  a generation-swap path exists — adding a code today would make the
  append-only list describe behaviour no code emits, which is the defect class
  this record exists to catch. The mapping is sequenced with the swap path.
  `WasmPlugin::drain` likewise has no production caller for the same reason:
  there is no swap or unload path to call it from, so it is proven by test
  only and recorded in §6 rather than implied to be wired.

- **Wave M4 — a release is now content-addressed: `kelson build` records each
  binary's SHA-256, and `kelson release --verify` refuses one that no longer
  hashes to it.**

  **The gap.** `release.json` described a release as *what* — name, version,
  profile — and never as *which bytes*. The crate's own doc comment said
  "what an operator promotes is a named artifact, never 'whatever is in
  target/'", but the manifest could not tell an operator whether the
  `kelson-demo.exe` on a mirror is the one that was built. Promotion between
  two machines, or after a rebuild on the same one, rested on a filename. The
  pair migrations already had digests (Phase S); the binaries did not.

  **What changed.** `Artifact` gains `sha256: Option<String>`, taken from the
  bytes on disk by a single shared `sha256_hex` that pair-migration digests now
  go through too — one formatter, so a migration hash and a binary hash can
  never disagree on encoding while both are compared against hashes recorded
  elsewhere. `kelson build` fails rather than recording a digest it did not
  take, for the same reason it already fails rather than shipping an incomplete
  migration set: a manifest that cannot be verified later will one day be
  read as an all-clear. `kelson release --verify` re-hashes every artifact and
  distinguishes three failures instead of collapsing them into one, because
  each has a different remedy — **Mismatch** (investigate), **Missing**
  (rebuild), **Undigested** (the manifest predates Wave M4; re-run `kelson
  build`). The third is reported as a *failure*, never skipped: "nothing was
  checked" and "everything checked out" must not share an exit code. Plain
  `kelson release` still prints the manifest exactly as before; `--verify` is
  an opt-in flag, not a new subcommand.

  **Backward compatibility is the load-bearing part.** `sha256` carries the
  same `#[serde(default)]` Phase S gave `ReleaseManifest::migrations`, so a
  pre-digest `release.json` still parses — with the field as `None`, which
  `--verify` then reports as cannot-tell rather than treating as a pass. A
  pinning test builds a pre-M4 manifest and asserts it reads.

  **Evidence — all five verdicts observed live on this machine.** `kelson build`
  (profile `release`) printed three digests and wrote them into `release.json`.
  `kelson release --verify` against that intact manifest exited **0** with
  three `[ok]` lines. Corrupting one recorded digest and re-running exited
  **1** with `digest MISMATCH (recorded 0000...0000, on disk 8784cd6a...)`.
  Deleting a digest field — making it a pre-M4 manifest — exited **1** with
  "manifest records no digest (cannot tell)". Renaming `kelson-worker.exe` away
  exited **1** with "not found at …". With no manifest at all, plain `kelson
  release` still exits **0** on its usual message while `--verify` exits **1**.
  Restoring both inputs returned **0**, so the verdicts track only the manifest
  and the bytes on disk. Underneath, `sha256_hex` is pinned against the
  published SHA-256 of `""` and of `"kelson"`, so a later edit to the formatter
  cannot silently change the encoding every recorded hash is compared under,
  and a pre-digest manifest is asserted to still parse with the field as
  `None`.

  **Honest limits.** This is *integrity*, not *authenticity*: `release.json` is
  plain JSON, so anyone who can rewrite it can forge matching bytes — that is
  backlog finding 18, deliberately still open. `--verify` re-hashes what is on
  disk, so it cannot tell you the *right* binary was built from the *right*
  source, only that this binary is the one the manifest describes. And
  `artifact_path` derives the `.exe` suffix from `cfg!(windows)` — the host —
  so a manifest built on one OS and verified on another resolves to a different
  path and reports Missing; the digests remain comparable, the paths do not.

  **Gates.** Workspace 1388 passed / 0 failed / 3 ignored against the 1382
  baseline (+6: the digest pinned to published constants, hashing the file it
  is given, the profile path shape, a pre-digest manifest still parsing, the
  three failure verdicts of `verify_artifacts`, and the `--verify` flag shape).
  `clippy --all-targets -D warnings` clean. `kelson-demo --features demo` 221
  / 0, unchanged. One test was wrong on the first run — it wrote straight to
  `manifest_path` instead of through `write_manifest`, so it failed on a missing
  parent directory rather than on anything it meant to assert; it now writes
  through the production path and additionally asserts the fixture on disk has
  no `sha256` key at all, so it cannot pass by round-tripping the very field it
  is meant to prove unnecessary.
- **Wave M3 — `kelson migrate:plan` previews what `migrate` would apply and
  checks it against the expand-and-contract rule, which until now existed only
  as prose.**

  **The gap.** `docs/rust/10-STRUCTURE-AND-GUIDELINES.md` states the migration
  authoring rule — add nullable/with-default, backfill, switch reads, drop the
  old column in the NEXT release, `CREATE INDEX CONCURRENTLY`, no table-rewrite
  locks during business hours — and verification-doc finding 22 recorded the
  result: "documented practice, no tooling". Nothing looked at a migration
  before running it, so the first warning a wrong migration produced was the one
  the database produced while applying it. The rule was enforceable only by a
  human reading a diff.

  **What changed.** `kelson migrate:plan` prints what `migrate` WOULD apply —
  the forward-only set for the connected driver plus the pending pairs, in
  order — and scans exactly that set against four codes, all derived from the
  sentence above rather than invented for the command:

  - `EAC-001` (fatal) — a migration that both `ADD COLUMN`s and `DROP`s is
    shipping expand and contract in one release. A drop-only migration is
    allowed: that *is* the next release.
  - `EAC-002` (fatal) — `CONCURRENTLY` without a `-- no-transaction` first
    line. This one was found rather than assumed: sqlx keys that exact string
    (`sqlx-core 0.8.6`, `src/migrate/source.rs:127`) and otherwise wraps every migration
    in a transaction, which Postgres refuses for `CONCURRENTLY`. The migration
    would error at apply time, so it is not advisory.
  - `EAC-003` (advisory, PostgreSQL only) — plain `CREATE INDEX`. Advisory
    because it had to be: **measured, 9 of 9** migrations on *each* driver
    build their indexes without `CONCURRENTLY`, so a fatal verdict would
    condemn applied history instead of new work and fail CI for a change nobody
    is making. And PostgreSQL-only because MySQL has no `CONCURRENTLY` at all —
    reporting its absence there would be a defect in the command, not in the
    migration.
  - `EAC-004` (fatal) — an `ADD COLUMN` that is `NOT NULL` with no `DEFAULT`,
    the rule's first clause. The column declaration is read only up to the next
    `CHECK`/`CONSTRAINT`, so an inline `CHECK (x IS NOT NULL)` naming another
    column cannot be mistaken for a missing default (that false positive is
    pinned by a test).

  `migrate:status` and `migrate:plan` now read through the same three helpers
  (`applied_versions`, `applied_pair_names`, `scanned_pair_sql`), so the plan
  cannot drift away from what `migrate` actually does.

- **Wave M2 — a WASM plugin can declare its own `[budget]`, and the two bounds
  fuel never covered are now enforced.**

  **The gap.** Fuel (`DEFAULT_FUEL` = 10M) and the 16 MiB memory cap were the
  only per-plugin limits, and both are ceilings the *host* sets identically for
  every plugin. A plugin that legitimately needs a smaller sandbox had no way to
  say so, and two failure modes had no bound at all. A plugin that runs *slowly*
  rather than looping could pin a worker indefinitely, because fuel measures
  work done and nothing anywhere measured time spent. And a plugin accepting
  concurrent calls could be driven past any useful degree of saturation, with
  every incoming call still instantiated and run regardless.

  **`[budget]` can only tighten, and is checked before the binary is compiled.**
  `max_memory_mb`, `max_fuel`, `max_concurrency` and `execution_timeout_ms` each
  may only *lower* a host ceiling. A manifest that asks for more is a load
  refusal naming **every** violation at once, not a negotiation and not a
  silent raise: the direction is the whole safety property, since a third-party
  module must not be able to widen the sandbox an operator configured, and a
  check that stopped at the first violation would send an operator back to
  their editor once per attempt. Validation runs at the top of
  `WasmHost::load`, before a byte is compiled or instantiated.

  **Two enforcement points.** `max_concurrency` is taken *before* the guest is
  instantiated, so a saturated plugin sheds load rather than queueing it.
  `execution_timeout_ms` is enforced with wasmtime epoch interruption
  (`Config::epoch_interruption`, `Store::set_epoch_deadline`,
  `Engine::increment_epoch`), which interrupts a guest at its own loop
  back-edges.

  **The ticker counts a clock, not sleep calls — the defect this avoided.**
  The epoch advances once per *tick*, so ticks must correspond to
  milliseconds. Counting one tick per `sleep(1ms)` does not achieve that:
  `sleep` is a lower bound, and on Windows the default timer resolution lands a
  1ms sleep near 15.6ms, so a declared 50ms deadline would have fired around
  780ms — late by a factor that varies per machine. The ticker therefore reads
  a monotonic clock and catches the epoch up by the milliseconds that have
  actually elapsed. The consequence, stated plainly: a deadline may run *late*
  by up to one sleep interval plus OS timer slop, but never early, and never by
  a multiple of the budget. It is a coarse bound, as wasmtime's own
  documentation says epochs are, not a precise timeout.

  **Every store gets a deadline, because wasmtime's default is a trap.**
  With epoch interruption enabled, a store's deadline starts at `0`, which
  wasmtime documents as having "always elapsed" — a store left at the default
  traps its guest before it runs one instruction. Plugins that declare no
  timeout are therefore given `NO_DEADLINE_TICKS` (`u64::MAX / 2`, not
  `u64::MAX`, because the deadline is computed as `current_epoch + ticks` and
  would overflow it). All 14 pre-existing WASM tests still pass, which is the
  evidence that this was handled.

  **Two new append-only codes, both pinned to HTTP 503** beside the existing
  `KSN_WASM_FUEL`: `KSN_WASM_SATURATED` and `KSN_WASM_DEADLINE`. The
  ResourceExhausted default of 429 would tell the caller it was rate limited
  when it was our plugin's slot or clock that ran out. The deadline
  deliberately does **not** reuse the platform's existing `KSN_DEADLINE`:
  `ErrorRenderRegistry::set_status` is a *global* per-code override, and that
  code already renders from two other sites' own categories (the execution
  engine's `Internal`/500, a worker job's `Workflow`/409), so pinning it here
  would have silently re-skinned both. A plugin's wall-clock budget is a
  sandbox budget in the same family as `KSN_WASM_FUEL`, so it takes a sibling
  code.

  **`[budget]` is host policy, never guest state.** A guest's
  `kelson_manifest()` has no way to declare it and no reason to. Comparing it
  during the drift check would have refused *every* budgeted plugin as drifted,
  so both documents are cloned with `budget` cleared before the comparison —
  name, version, capabilities and ABI still compare byte for byte.

  **The ticker is started on demand and held by the plugin.** It exists only if
  some loaded plugin declares a deadline, so a fuel-bounded workspace starts no
  thread at all. It is held by `WasmPlugin`, not by `WasmHost`, because
  `load_wasm_plugins` drops its host before any handler is dispatched — a
  plugin that did not hold its own reference would see its deadline silently
  stop firing.

  **Evidence.** Three new tests in `runtime/kelson-demo/src/wasm_tests.rs`
  (`a_budget_asking_for_more_sandbox_than_the_host_refuses_boot`,
  `a_wall_clock_deadline_interrupts_a_spinning_guest_and_pins_503`,
  `a_saturated_plugin_refuses_a_call_before_a_guest_is_instantiated`) over two
  new fixtures that reuse the checked-in `.wat` binaries and vary only
  `[budget]`. The deadline test runs `spin.wat` against a host with a
  near-unbounded fuel cap so fuel cannot win the race and the interrupt is
  unambiguously the epoch deadline; the saturation test holds the single slot
  from a spawned call and asserts the second is refused in under 100ms, which
  is what distinguishes refusal from queueing-and-running. Full gates unchanged
  in kind and green: **1380 passed / 0 failed / 3 ignored** (`cargo test

  by cargo for `home`, `icu_*`, `time` and `wasm-{encoder,wast,wat}` 261 (all
  requiring 1.88), and `uuid 1.27.0` ("requires rustc 1.89.0") pushes the three
  non-platform roots to 1.89; `platform` resolves the older `uuid 1.24.1` and
  stops at 1.88. Each floor is verified by a real `cargo check --workspace
  --locked` on that exact toolchain. Updated in all four workspace roots,
  `DEPENDENCY-POLICY.md` and `docs/01-GETTING-STARTED.md`.
- **The `msrv` CI gate was a silent no-op; it is real now.**
  `platform/rust-toolchain.toml` pins channel 1.92.0 and rustup resolves that file
  *above* `rustup default`, so installing 1.86.0 and setting it as the default
  still built 1.92.0 — the job reported the floor as met without ever testing it.
  It now sets `RUSTUP_TOOLCHAIN` (which outranks the file, verified by resolving
  1.92.0 normally and 1.86.0 with the variable set) and runs a per-workspace
  matrix, one leg per verified floor.
- **CI: one pipeline split into four.** `.github/workflows/keel.yml` now has a
  job per Cargo workspace with its own `working-directory` and target cache. The
